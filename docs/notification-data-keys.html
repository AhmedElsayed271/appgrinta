شرح مفاتيح الإشعار — type = reminder

مثال لإشعار «المباراة على وشك البدء» (يُرسل قبل المباراة بـ 45 دقيقة) بعد معالجة الـ normalizePayload.

"type": "reminder", "data": { "match_id": "123", "fixture_id": "456789", "home_team_id": "1", "away_team_id": "2", "type": "system", "id": "123", "post_id": "" }, "is_read": false, "created_at": "2026-10-06T15:15:00.000000Z"

المفاتيح الخارجة (الـ outer keys)

Keyالشرح
type عمود الـ type في قاعدة البيانات. هنا قيمته reminder يعني إشعار التذكير بالمباراة (يُرسل قبل البدء بـ 45 دقيقة). ده اللي المفروض تعتمد عليه في عرض الإشعار / التصنيف.
data الـ payload اللي بتتنقل بيه الشاشة — فيه مفاتيح التنقل المهمة للموبايل.
is_read هل الإشعار مقروء أم لا. القيمة false = لسه متقرياش → يظهر في الـ unread badge.
created_at وقت الإرسال/التخزين بصيغة UTC (timestamp).

المفاتيح جوه الـ data

Keyالشرح
match_id معرّف الماتش في داتابيزك (matches.id) → بيستخدم لفتح شاشة الـ Match Detail مباشرة.
fixture_id معرّف الماتش في Football-API الخارجي → بيستخدم لو في حاجة بتتشاور بيه عند API تاني.
home_team_id معرّف الفريق المضيف في الداتابيز (teams.id) → بيسمح بفتح صفحة الفريق أو إبراز الفريقين.
away_team_id معرّف الفريق الضيف في الداتابيز (teams.id).
type مفتاح اتضاف من normalizePayload وأخد القيمة الافتراضية system لأن الـ payload الأصلي (match_id / fixture_id / team ids) مكانش فيه type. مهم: عادي يبقى system حتى لو عمود الـ type الحقيقي هو reminder — متعتمدش عليه جوه الـ data.
id اتضاف كمان من normalizePayload: بياخد أول key متاح من قائمة [post_id, match_id, fixture_id, team_id, competition_id, player_id, notification_id] فا أخذ قيمة match_id (123). ده "navigation id" عام يصلح لو عايز id واحد بس.
post_id فاضي "" لأن النوع مش post — المفتاح ده بيتظبط بس لإشعارات البوستات (type = post).

الخلاصة للـ App

عند الضغط على الإشعار:
data.match_id → يفتح الماتش  ·  home_team_id / away_team_id → التفاعل مع الفريقين  ·  fixture_id → لو محتاج الـ API الخارجي.
data.type → يتم تجاهله تجنبًا للخلط مع عمود الـ type إذا كان system.
